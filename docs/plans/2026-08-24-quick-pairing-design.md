# OpenPaw Quick Pairing Design

**Date:** 2026-08-24

**Status:** Approved

**Goal:** Let a user scan a QR code or open a pairing link, explicitly confirm the SSH credential, and then have OpenPaw automatically save the host, establish SSH, redeem the existing one-time host pairing code, persist structured API credentials, and open Terminal. The same Quick Connect surface replaces the current Home Tailnet-candidate path that incorrectly falls back into the generic Add Device flow.

## Product decision

OpenPaw will use one unified **Quick Connect** flow for three entry points:

1. Scanning a QR code printed by `openpaw-host pair --qr`.
2. Opening an `openpaw://pair#...` link.
3. Tapping a Tailnet candidate such as “MacBook Pro” on Home.

The app may automatically select the last successful credential for the same SSH target, but it must always show the selected credential and require an explicit **Confirm SSH credential and connect** action. It must never automatically submit a password, private key, or agent identity merely because a QR code or candidate row was opened.

After confirmation, the app performs the remaining steps automatically and reports progress at the exact failing stage:

```text
validate proposal
→ save/select host
→ establish SSH and verify host key
→ open the loopback host-API tunnel
→ redeem the five-minute single-use pairing code, if present
→ save the returned token/HMAC signer in Keychain
→ route to Terminal
```

A Tailnet candidate without a pairing code still reaches the same surface. It can establish and save the SSH host immediately, while structured OpenPaw pairing remains clearly marked as unavailable until a code or link is supplied.

## Security boundary

The QR code and pairing link may contain only short-lived or public connection metadata:

- envelope version
- display name
- ordered SSH targets, preferring MagicDNS, then Tailnet IP, then an explicitly supplied hostname
- SSH username and port
- SSH host-key fingerprints, when the host can provide them safely
- OpenPaw loopback daemon port
- capability profile
- one-time pairing code
- issue and expiry timestamps
- opaque pairing session identifier

They must never contain:

- a password
- a private key or passphrase
- a Keychain reference
- a device bearer token
- an HMAC signing key
- provider credentials
- arbitrary shell text or a command to execute

The existing host pairing properties remain authoritative: codes are generated by the running daemon, held only in memory, expire after five minutes, are consumed once, and return device credentials exactly once. A scanned proposal does not establish trust by itself. SSH host-key verification remains mandatory before credentials are presented. The app shows the target, fingerprint, requested capability profile, and selected SSH credential before connecting.

The pairing payload is transported in the URL fragment rather than query parameters:

```text
openpaw://pair#v1.<base64url-encoded-envelope>
```

This keeps the short-lived code out of ordinary web-server query logs if an HTTPS Universal Link is added later. The first release uses the already-registered `openpaw` custom scheme and a native scanner, with no cloud relay or pairing website.

## Pairing envelope

The protocol uses a bounded, versioned value type rather than free-form URL fields:

```text
PairingEnvelopeV1
  version: 1
  sessionID: bounded opaque identifier
  displayName: bounded printable text
  targets: [SSH target], bounded count
  username: bounded SSH username
  sshPort: 1...65535
  hostKeyFingerprints: bounded list of recognized algorithms and SHA-256 fingerprints
  hostAPIPort: 1...65535
  profile: observer | operator
  pairingCode: normalized existing OpenPaw code
  issuedAt: RFC3339
  expiresAt: RFC3339, no more than five minutes after issuance
```

The decoder rejects unknown versions, duplicate required fields, control characters, oversized payloads, invalid hostnames or addresses, unsupported fingerprint algorithms, expired timestamps, and URLs containing credentials in their authority. Decoding produces a pure `QuickConnectProposal`; it never mutates the host store or Keychain.

The initial wire representation should be compact JSON encoded as UTF-8 then base64url without padding. This is easy to inspect and test while remaining small enough for a QR code. A future version may use CBOR only if real payload size requires it.

## Mac CLI experience

`openpaw-host pair --qr` requests a pairing code from the already-running loopback daemon through the existing hook-token-authenticated endpoint. The CLI then gathers only local public metadata, builds the envelope, and prints:

1. A terminal-rendered QR code.
2. The equivalent `openpaw://pair#...` link.
3. Human-readable target, profile, and expiry information on stderr.

Machine-readable output remains selectable through an explicit format option so existing `pairing-code | pbcopy` behavior is not broken. QR generation is presentation only. The daemon remains the sole issuer and consumer of pairing codes.

If the CLI cannot determine a safe SSH username, routable target, or host-key fingerprint, it omits or clearly marks the missing value instead of guessing. The iPhone then requires the user to fill or verify that field.

## iOS experience

Home gains a **Scan pairing QR** action. Scanning uses the native camera stack and accepts only OpenPaw pairing payloads. The camera purpose string is updated to mention device pairing as well as attachments.

A valid proposal opens `QuickConnectView`, which shows:

- “Quick Connect to <device>”
- exact SSH target and port
- username
- selected credential and Change action
- host-key fingerprint or “verify on first connection”
- OpenPaw profile and pairing-code expiry
- one primary action: **Confirm SSH credential and connect**

Credential selection follows this order:

1. Last successful credential explicitly associated with the same normalized SSH target.
2. Another saved compatible credential selected by the user.
3. Import private key or choose password-backed authentication.

A credential may be preselected but is never submitted without the primary confirmation action.

Tapping a Home Tailnet candidate creates the same proposal and opens `QuickConnectView` directly. It must not set `isAdding` or present `AddDeviceFlow`. The generic Add Device flow remains available for manual SSH entry, administrator discovery configuration, and advanced edits.

## Connection coordinator

A dedicated `QuickConnectCoordinator` owns the automatic sequence. It uses generation or request ownership tokens so a late completion from one candidate cannot overwrite a newer user choice.

The coordinator must not persist a half-valid host before the user confirms. After confirmation it may upsert the host, select it, and begin the connection. If SSH fails, the editable proposal and credential selection remain visible. If SSH succeeds but OpenPaw pairing fails, Terminal remains available over plain SSH and the screen explains that structured features are not yet paired. Retrying pairing does not reopen or duplicate the SSH connection unnecessarily.

Host-key mismatch is terminal for the attempt. The app must not silently replace a pinned fingerprint from the QR, an existing saved host, or a prior successful connection. Expired and consumed pairing codes require a newly generated QR/link but do not delete a successfully saved SSH host.

## Error presentation

Progress and failures are typed by stage:

- invalid or unsupported pairing link
- pairing link expired
- incomplete SSH target
- SSH credential missing
- host-key verification required
- host-key mismatch
- SSH authentication failed
- host API unavailable over the tunnel
- pairing code rejected or already consumed
- Keychain persistence failed
- navigation superseded by a newer request

No error falls back to the Add Device welcome screen. The user remains on Quick Connect with the exact field or stage that needs attention.

## Verification

Required tests:

- Pure envelope round-trip, bounds, malformed input, expiry, unsupported version, and secret-exclusion tests.
- Rust CLI tests proving QR/link output contains the existing daemon-issued code and no hook token or persistent credential.
- Swift coordinator tests covering automatic host save, SSH connect, pairing redemption, Keychain persistence, Terminal routing, stale-request suppression, host-key mismatch, and plain-SSH fallback when structured pairing fails.
- Home presentation tests proving a Tailnet candidate maps to Quick Connect rather than Add Device.
- XCUITest launching a deterministic QR proposal, confirming the SSH credential, observing each automatic stage, and ending on Terminal.
- A regression XCUITest that taps the visible “MacBook Pro” candidate and asserts that neither the Add Device title nor onboarding actions appear.
- Live disposable-host acceptance using a real SSH daemon and `openpaw-host`: generate a real code/link, open it in the simulator or physical iPhone, confirm the credential, pair, and reach an interactive Terminal.

Snapshots remain useful for layout but do not count as navigation or pairing acceptance.
